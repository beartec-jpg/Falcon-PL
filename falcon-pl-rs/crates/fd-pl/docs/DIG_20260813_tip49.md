# DIG-20260813 — tip=49 / empty mempool (not a consensus freeze)

| | |
|--|--|
| Date | 2026-08-13 |
| Product | Falcon PL **2.6.0** |
| Mesh | host1 v1/v2 + host2 v3, `network_id=2200`, Falcon-512 |
| Checklist | C19 |

## Observation

After the v2.6 catch-up / slim-Hello cut, all three hubs sat at **tip=49 hash `3ef4adca…`**, `mempool=0`, `pending=None`, `lottery_winner_next=v3`, load-net still alive (~16 min past `--seconds 360`).

Review (`REVIEW_v2.6.0.md`) asked whether this was a drained inject window or a liveness bug.

## Verdict: **inject hang, not a fork / not open-height stall**

Evidence:

1. **Same tip + same hash on all hubs.** No dual pending, no state-root conflict, no `need_hard_resync`.
2. **Mempool empty everywhere** — nothing to pack. Winner v3 correctly not sealing empty ledgers.
3. **load-net Recv-Q** on RPC sockets was megabytes (especially host2 `:19111`). Process still `Sl`, 0.1% CPU, no result log after `--seconds` elapsed. Client was not draining replies, so submits stopped.
4. **Restart of load-net only** (nodes left up, seq-file resynced from chain: 1012/1024 wallets) advanced **49 → 100+ → 158** with **3-way hash agreement**.

That is the opposite of the tip-32 poison freeze (non-empty future-only mempool + closed pack/skip/VC gates).

## Not this class

- Seq-poison pipeline wipe (AMD-20260813-2) — mempool was empty, not future-only.
- Solo soft QC / pong-cap fork — hashes agreed.
- Catch-up / Hello 1.9MB stall — already fixed; v3 had caught up to 49.

## Follow-up (ops, not protocol)

- Treat `load-net` stuck past `--seconds` with Recv-Q as an inject-tool bug (drain timeout / smaller reply bodies).
- Do **not** “fix” by deferring `SubmitTx` when `tip==0 && best_peer==0` (that froze the whole cold mesh).
- C20 soak: hours of agree under a **watched** load (kill+restart inject if Recv-Q explodes).
